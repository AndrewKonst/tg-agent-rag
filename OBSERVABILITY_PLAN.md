# План: observability и оптимизация токенов

Цель задания: видеть, куда уходят токены, и сократить стоимость запуска минимум на 30%, не потеряв больше 2% success rate.

## 0. Что уже выяснено про источники данных

Проверено эмпирически (пробный вызов Koog → Ollama, `qwen3:0.6b`):

```text
total=94  input=24  output=70  model=null  metadata=null
```

Значит:

- **`input_tokens` / `output_tokens` / `total`** — приходят от провайдера, считать самим не надо;
- **`model`** — в metaInfo пусто, берём из конфига агента;
- **`cached_tokens`** — Ollama не сообщает (и в Koog нет такого поля). Провайдерского кеша здесь нет вообще, поэтому вместо выдуманной цифры считаем **свою** метрику: сколько входных токенов на этом turn — это префикс промпта, дословно совпадающий с предыдущим turn, то есть то, что *было бы* cache hit у OpenAI/Anthropic. Называем это в дашборде `prefix reuse (cacheable)`, а не `cache hit`, чтобы не врать;
- **`reasoning_tokens`** — qwen3 присылает `<think>…</think>` внутри текста, и мы это уже вырезаем в `stripInlineReasoning`. Значит reasoning-токены реально измеримы: это токены вырезанного блока.

## 1. Мониторинг (Часть 1)

Новый пакет `observability/`.

- `MeteredLlm : Llm` — декоратор вокруг каждого вызова модели. Пишет: timestamp, agent_id, task_id, model, turn_number, input/output/reasoning tokens, prefix-reuse, latency, estimated_cost.
- `MeteredTool : AgentTool` — декоратор вокруг каждого tool. Пишет: tool_name, input_size, output_size, output_tokens, duration.
- `RunRecorder` — собирает записи одного run и закрывает его итогом (turns, tool calls, стоп-причина, успех).
- `ObservabilityStore` — SQLite: `runs`, `llm_calls`, `tool_calls`. Отдельная база, чтобы аудит не мешал рабочим данным.
- `TokenReport` — рендер ASCII-дашборда и timeline одного запуска.
- В Telegram: `/stats` (дашборд) и `/trace` (последний запуск по turn'ам). Плюс CLI-точка входа для отчёта из базы.

Разбивка контекста (`system / user task / tool outputs / history`) считается своим оценщиком по сообщениям и **масштабируется на реальный `input_tokens`** от провайдера: суммарное число измерено, а пропорции оценены. Это указывается в отчёте, чтобы не выдавать оценку за факт.

## 2. Аудит (Часть 2)

По собранным данным получить:

- какой tool генерирует больше всего токенов (доля в output токенах tool'ов);
- самый дорогой turn;
- что растёт быстрее всего: history / tool outputs / system prompt / user task;
- сколько input-токенов — это уже виденная моделью информация.

## 3. Оптимизации (Часть 3, минимум 3)

Кандидаты, от самого крупного эффекта к меньшему:

1. **Сжатие истории** — сейчас в каждый run переигрывается до `CONVERSATION_MAX_CHARS` символов истории целиком. Резать старые turn'ы агрессивнее и/или суммаризовать.
2. **Обрезка tool output'ов** — `search_documents` отдаёт 5 чанков по 1000 символов целиком; `exec` до 4000 символов. Отдавать релевантные фрагменты и лимит на chunk.
3. **Стабильный префикс промпта** — держать system prompt и описания tool'ов дословно неизменными, чтобы префикс переиспользовался (и был cache hit у платных провайдеров).
4. **Не переигрывать reasoning** — `<think>` уже не хранится, проверить, что и tool-результаты старых turn'ов не тащатся целиком.
5. **top-K и длина чанка в RAG** — 5×1000 символов на каждый вопрос по документам.

## 4. Benchmark (Часть 4)

Фиксированный набор задач (вопросы по документам + tool-задачи), прогон до и после, замер: токены, стоимость, turns, tool calls, success rate. Успех задачи — проверяемый предикат (ожидаемая подстрока или ожидаемый вызов tool), а не «на глаз».

Критерий приёмки: **−30% токенов и не более −2% success rate**.
