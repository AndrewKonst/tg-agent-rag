# План реализации RAG для Telegram AI-агента

Цель: пройти задание по этапам так, чтобы было понятно, как устроен весь RAG pipeline: от загрузки документа в Telegram до ответа агента с источником.

## Статус (10 сентября 2026)

Все этапы плана реализованы:

- extraction `.txt` / `.md` / `.pdf` / `.docx` — `rag/DocumentTextExtractor.kt`;
- chunking 1000/150 — `rag/TextChunker.kt`;
- embeddings `all-MiniLM-L6-v2` (384d) через Ollama, с lexical fallback — `rag/OllamaEmbeddingService.kt`, `rag/EmbeddingService.kt`;
- хранение и vector search на sqlite-vec, изоляция по `user_id` — `rag/SqliteRagStore.kt`;
- загрузка документа прямо из Telegram, команды `/documents`, `/delete`, отладочные `/save_docs` и `/search_docs` — `telegram/TelegramBot.kt`, `telegram/MessageHandler.kt`;
- retrieval как tool агента `search_documents(query)` — `tools/SearchDocumentsTool.kt`;
- обработка ошибок: формат, размер, битый файл, пустой документ, недоступная embedding-модель, ошибки SQLite/LLM/Telegram;
- evaluation из 5 вопросов — `data/rag-eval/questions.json`, `RagEvaluationTest`;
- 134 теста, включая проверку того, что модель сама вызывает `search_documents`.

Документация по архитектуре, chunking, embeddings, ограничениям и тестам — в `README.md`.

Результат:

- понятно, куда встроить RAG tool;
- есть схема текущего потока: Telegram -> Agent -> LLM -> Telegram.

Проверка:

## 2. Сделать извлечение текста из документов

Что делаем:
- добавляем поддержку `.txt`;
- добавляем поддержку `.md`;
- добавляем поддержку `.docx`;
- добавляем поддержку `.pdf`.

Пример будущей функции:

```python
extract_text(file_path: str) -> str
```

Результат:
- любой поддерживаемый файл превращается в обычный текст.

Проверка:
- для каждого формата есть тестовый файл;
- из каждого файла извлекается непустой текст;
- неподдерживаемый формат возвращает понятную ошибку.

## 3. Реализовать chunking

Что делаем:
- разбиваем большой текст на небольшие fragments/chunks;
- выбираем размер chunk;
- выбираем overlap;
- сохраняем индекс chunk внутри документа.

Рекомендуемый стартовый вариант:
- chunk size: 800-1200 символов или примерно 300-500 токенов;
- overlap: 100-200 символов или примерно 50-100 токенов.

Результат:
- текст документа превращается в список chunks.

Проверка:
- короткий текст дает один chunk;
- длинный текст дает несколько chunks;
- соседние chunks немного пересекаются;
- пустой документ обрабатывается как ошибка.

## 4. Подключить embeddings

Что делаем:
- выбираем embedding model;
- реализуем функцию получения embedding;
- фиксируем размерность vector;
- обрабатываем ошибку embedding model.

Пример будущей функции:

```python
embed_text(text: str) -> list[float]
```

Результат:
- каждый chunk можно превратить в vector.

Проверка:
- embedding создается для обычного текста;
- размер vector совпадает с документацией модели;
- ошибка API или локальной модели не ломает бота.

## 5. Спроектировать SQLite + sqlite-vec

Что делаем:
- создаем таблицу `documents`;
- создаем таблицу `chunks`;
- создаем vector table через `sqlite-vec`;
- связываем vector с chunk;
- обязательно храним `user_id`.

Минимальная логика связей:

```text
users are represented by Telegram user_id
   |
documents.user_id
   |
chunks.document_id
   |
vectors.chunk_id
```

Результат:
- база хранит документы, chunks и embeddings;
- по найденному vector можно получить chunk и filename.

Проверка:
- можно добавить документ;
- можно получить его chunks;
- можно удалить документ вместе с chunks и embeddings.

## 6. Реализовать индексацию документа

Что делаем:
- принимаем файл из Telegram;
- скачиваем файл;
- извлекаем текст;
- разбиваем на chunks;
- создаем embeddings;
- сохраняем все в SQLite.

Пользовательский поток:

```text
Document received
-> Extracting text
-> Creating chunks
-> Generating embeddings
-> Saving to SQLite
-> Document ready
```

Результат:
- после отправки файла бот отвечает, что документ обработан;
- документ появляется в `/documents`;
- chunks и vectors есть в базе.

Проверка:
- загружаем `.txt`, `.md`, `.docx`, `.pdf`;
- каждый файл индексируется;
- слишком большой или поврежденный файл дает понятное сообщение.

## 7. Реализовать retrieval

Что делаем:
- получаем вопрос пользователя;
- создаем embedding вопроса;
- ищем Top-K похожих chunks через sqlite-vec;
- фильтруем поиск по `user_id`;
- возвращаем chunks с filename и метаданными.

Пример будущей функции:

```python
search_documents(user_id: int, query: str, top_k: int = 5) -> list[SearchResult]
```

Рекомендуемый старт:
- `top_k = 5`.

Результат:
- по вопросу находятся релевантные chunks только из документов текущего пользователя.

Проверка:
- вопрос по документу возвращает правильный chunk;
- User A не видит chunks User B;
- если информации нет, retrieval возвращает пустой или слабый результат.

## 8. Подключить RAG как tool агента

Что делаем:
- добавляем tool `search_documents`;
- агент вызывает tool, когда вопрос относится к документам;
- найденные chunks передаются в LLM как context;
- LLM отвечает только на основе context.

Важно:
- не добавлять все документы в system prompt;
- не использовать общие знания LLM как ответ из документа;
- если ответа нет, честно сообщать: "Я не нашел этой информации в загруженных документах."

Результат:
- агент умеет отвечать на вопросы по документам;
- ответ содержит источник.

Проверка:
- задаем вопрос по загруженному документу;
- получаем правильный ответ;
- в ответе есть `Источник: filename`;
- вопрос не по документам не должен ломать обычный сценарий агента.

## 9. Добавить Telegram-команды

Что делаем:
- добавляем `/documents`;
- добавляем `/delete filename`;
- при удалении документа удаляем:
  - запись из `documents`;
  - связанные `chunks`;
  - связанные embeddings.

Результат:
- пользователь может посмотреть список своих документов;
- пользователь может удалить документ.

Проверка:
- `/documents` показывает только документы текущего пользователя;
- `/delete vacation_policy.pdf` удаляет документ;
- после удаления документ не участвует в search.
