# Промт: оптимизация расхода токенов

Самодостаточное задание. Все числа в нём — результат измерения, а не оценки; источники указаны.

## Контекст

Репозиторий: `tg-agent-rag`, ветка `main`.
Kotlin 2.3 / JVM 21, Gradle. Telegram-бот с RAG-агентом; модель локальная — `qwen3:14b` через Ollama.

Слой измерения уже готов и закоммичен:

- `observability/` — middleware вокруг каждого вызова модели (`MeteredLlm`) и каждого инструмента (`MeteredTool`), трейсы в SQLite, дашборды;
- `benchmark/` — 10 задач с предикатами успеха и прогон обеих веток сравнения;
- `reports/` — выгруженная базовая линия (она в git, в отличие от `data/`, которая игнорируется);
- `TOKEN_AUDIT.md` — отчёт аудита.

Команды:

```bash
./gradlew benchmark --args="baseline"     # уже сделано, переделывать не нужно
./gradlew benchmark --args="optimized"    # твой прогон после правок
./gradlew benchmark --args="report"       # сравнение с вердиктом по цели
./gradlew benchmark --args="export"       # выгрузка в reports/
SQLITE_VEC_EXTENSION_PATH=$PWD/vendor/sqlite-vec/vec0.dylib ./gradlew test
```

Ollama должна быть запущена (`ollama serve`), модели: `qwen3:14b`, `all-minilm`.

## Цель

**−30% токенов на задачу при падении success rate не более чем на 2 pp.**

Порог проверяется автоматически: `benchmark --args="report"` печатает `MET` или `NOT MET`.

## Задачи

### 0. Починить атрибуцию контекста (сделать первым)

`PromptAudit.breakdown` считает только сообщения, а масштабирует результат к измеренному `input_tokens`. Всё, чего в сообщениях нет — схемы инструментов и chat template — размазывается по категориям пропорционально. Из-за этого дашборд показывал «system prompt 21%» вместо настоящих 8%.

Нужно: считать токены схем инструментов отдельной статьёй (`ToolDescriptor` доступен в `MeteredLlm.complete`) и завести явную категорию «unattributed overhead» для остатка вместо пропорционального размазывания.

Без этого нельзя проверить экономию по статьям 2 и 3 — она будет измеряться сломанной линейкой.

### 1. Урезать выдачу `search_documents` (цель: −25…30% всех токенов)

Сейчас один вызов отдаёт 4 214 символов: 5 чанков по 1000 символов целиком, строка со score и абзац инструкций, дублирующий системный промпт.

Сделать:

- `topK` 5 → 3, вынести в конфиг (`RAG_TOP_K`);
- вместо целого чанка отдавать окно ~400 символов вокруг места, где встречаются слова вопроса, расширенное до границ предложений (`RAG_EXCERPT_CHARS`);
- убрать строку со score и финальный абзац инструкций — он уже есть в системном промпте;
- **имя файла и номер чанка оставить**: на них держится цитирование источника, ради которого весь RAG и делался.

### 2. Отключить размышления (цель: −10…12%)

`qwen3` тратит почти весь выход на `<think>`, который затем вырезается в `stripInlineReasoning`. Мы платим за текст, который сами выбрасываем.

Сделать: отключить thinking (через параметр Ollama `think: false`, если он пробрасывается Koog, иначе через суффикс `/no_think` в системном промпте) и **обязательно замерить success rate** — без размышлений модель может хуже выбирать инструменты. Если success rate падает больше чем на 2 pp, оптимизацию откатить и записать это в отчёт как отрицательный результат.

### 3. Сжать схемы инструментов и системный промпт (цель: −10…15%)

Схемы — 28% входа и уходят в каждый запрос. Описание `search_documents` сейчас ~240 символов плюс ~90 символов на описание параметра.

Сделать: сократить описания инструментов и системный промпт, **не теряя поведения**: агент обязан по-прежнему сам вызывать `search_documents` на вопрос о документах, цитировать имя файла и отказываться отвечать, когда в документах ответа нет.

### 4. Компактная история (опционально)

В хранимой истории заменять длинные tool-результаты короткой выжимкой. Здесь выигрыш мал (история — часть тех 10%), но на длинных диалогах статья растёт быстрее всех. Делать только если после задач 1-3 порог не взят, либо как отдельный измеренный эксперимент.

## Что нельзя сломать

Эти свойства проверяются бенчмарком и тестами, их нарушение аннулирует результат:

1. **Источник в ответе.** Ответ по документам называет имя файла.
2. **Отказ вместо выдумки.** На вопрос, ответа на который в документах нет, агент говорит, что не нашёл. В наборе для этого есть две задачи: `absent-vacation-policy`, `absent-salary`.
3. **Follow-up работает.** Задача `follow-up-trial-length` отвечает на «а сколько он длится?» только при наличии истории. Обрезать контекст так, чтобы она сломалась, — не оптимизация.
4. **Изоляция пользователей.** Поиск фильтруется по `user_id`; это покрыто тестами, их нельзя ослаблять.
5. **Правила измерения одинаковы для обеих веток.** Менять то, *как* считаются токены, после записи baseline нельзя — иначе сравнение сравнивает линейки, а не оптимизации. Если правило всё же изменилось, baseline надо перезаписать целиком.
